## What's new in v1.3.0

A focused robustness + speed audit landed nine fixes on top of v1.2.1.
All changes are additive — no public-API breakage.

### Latency wins

| Path | Before | After | Change |
| --- | --- | --- | --- |
| `check_connect()` | 2000 ms (unconditional `sleep(2)`) | 0.0 ms (synchronous state read) | hits ~9 public methods every call |
| `realtime_price` cap | `list.pop(0)` — O(n) per tick | `deque(maxlen=1000)` — O(1) | bursty multi-asset streams no longer pay an n-tick penalty |
| Profile UTC offset | HTTP fetch per `open_pending` | cached for the session, reset on reconnect | one fewer HTTP RTT per pending |
| `start_realtime_sentiment` | 200 ms poll cycle | event-driven (`sentiment_ready_<asset>`) | wakes ~200× faster |
| `start_candles_one_stream` | 200 ms poll cycle | event-driven (`candle_generated_<asset>_<size>`) | same |
| `start_candles_all_size_stream` | 200 ms poll **+** re-issued `subscribe_all_size` every iteration (ban risk) | event-driven (`candle_generated_all_<asset>`) with single subscribe | same + no more poll-loop spam |
| `pending_ticket_map` close mirror | O(n) scan per close | O(1) reverse-index lookup (`_exec_to_pending`) | O(n²) → O(n) over a session |

### Reliability hardening

* `Quotex.connect()` is single-flighted via an internal `asyncio.Lock`
  — concurrent calls can no longer race into duplicate logins
  (account-lock risk).
* The heartbeat task now signals `status_changed=ERROR` on a send
  exception instead of silently breaking, so the reconnect supervisor
  wakes immediately.
* `stop_candles_stream(asset)` now drops the asset from the
  reconnect-replay lists (`subscribe_candle`,
  `subscribe_candle_all_size`) and the subscribe-once cache. Long
  sessions that rotate through assets no longer accumulate dead
  entries that get re-subscribed on every reconnect.
* The reconnect supervisor's belt-and-suspenders cleanup also drops
  `_active_pending` / `pending_ticket_map` / `_exec_to_pending` on
  every reconnect attempt, defending against a hard-error path that
  bypassed `_on_close`.

### Internals (informational; private — don't depend on these)

* `_exec_to_pending: dict[str, str]` on `QuotexAPI` — reverse index
  mirroring `pending_ticket_map`. Maintained automatically; the
  defensive fallback scan keeps the close handler correct even if
  someone bypasses the success path that populates the index.
* `Quotex._connect_lock`, `Quotex._profile_offset_cache`,
  `Quotex._subscribed_assets` — used for the wins above; not part
  of the public contract.

### Migration notes

None required. Every change is a drop-in. If your code was relying on
`check_connect()` to also act as a 2-second await/throttle, replace
the implicit pacing with an explicit `asyncio.sleep` where you want
it.

## Custom Proxy + DNS Overrides

`ProxyConfig` plumbs an HTTP/SOCKS proxy and per-host DNS overrides
through both the HTTP (httpx) and WebSocket transports.

```python
from pyquotex import Quotex, ProxyConfig

proxy = ProxyConfig(
    url="http://user:pass@proxy.example.com:8080",
    verify_ssl=True,
    dns_overrides={"qxbroker.com": "1.2.3.4"},
    extra_headers={"X-Forwarded-For": "203.0.113.10"},
)

client = Quotex(
    email="me@example.com",
    password="...",
    proxy_config=proxy,
)
```

| Field | Type | Purpose |
| --- | --- | --- |
| `url` | `str \| None` | Full proxy URL — `http://`, `https://`, `socks5://`, `socks5h://`. |
| `verify_ssl` | `bool` | Disable to skip TLS verification (use for raw-IP DNS overrides). |
| `dns_overrides` | `dict[str, str]` | Map hostname → IP. URL is rewritten to the IP and the original `Host` is preserved for SNI / cert validation. |
| `extra_headers` | `dict[str, str]` | Headers added to every HTTP and WebSocket request. |
| `use_browser_tls` | `bool` | Switch the HTTP backend to `curl_cffi` for browser-grade TLS (see next section). |
| `impersonate` | `str` | Target browser profile when `use_browser_tls=True`. Defaults to `"chrome120"`. |

You can also build a `ProxyConfig` from a JSON-style dict (handy for
configuration files):

```python
proxy = ProxyConfig.from_dict({
    "url": "socks5://h:1080",
    "dns_overrides": {"qxbroker.com": "1.2.3.4"},
})
```

> **TLS verification caveat.** When `dns_overrides` rewrites an HTTPS
> URL to a raw IP, default certificate verification will fail unless
> the target presents a cert valid for the IP. Set `verify_ssl=False`
> for the override path or terminate TLS at your proxy.

## Browser-Impersonating TLS (curl_cffi)

Modern bot-detection layers fingerprint TLS (JA3/JA4) and HTTP/2
settings. `httpx` emits a Python-style fingerprint that is trivially
distinguishable from a real Chrome or Firefox session. Setting
`use_browser_tls=True` swaps the HTTP backend to
[`curl_cffi`](https://github.com/yifeikong/curl_cffi), which emits a
real browser fingerprint.

```bash
pip install 'pyquotex[stealth]'
```

```python
proxy = ProxyConfig(
    url="http://residential-proxy:8080",
    use_browser_tls=True,
    impersonate="chrome120",  # or "firefox133", "safari17_2", "chrome116", …
)
client = Quotex(email="…", password="…", proxy_config=proxy)
```

Behaviour:

- When the `stealth` extra **is** installed, every HTTP request goes
  through `curl_cffi.AsyncSession`.
- When the extra is **missing**, a warning is logged and the client
  falls back to the default `httpx` backend — existing scripts keep
  working.
- WebSocket transport is unchanged; only HTTP fingerprints are
  affected.

## Multilogin Browser-Profile Bootstrap

`MultiloginConfig` integrates with the
[Multilogin](https://multilogin.com) v1 local agent or v3 cloud API.
On `connect()` the client starts the configured profile, fetches its
proxy + user-agent, and inherits both automatically.

```python
from pyquotex import Quotex, MultiloginConfig

multilogin = MultiloginConfig(
    profile_id="00000000-0000-0000-0000-000000000000",
    folder_id="my-folder",          # required for v3
    token="<bearer-token>",         # required for v3
    api="v3",                       # or "v1" for the local agent
    auto_start=True,
    auto_stop=True,
)

client = Quotex(email="…", password="…", multilogin=multilogin)
await client.connect()              # starts the profile, inherits proxy/UA
# … trade …
await client.close()                # stops the profile
```

If you also pass a `proxy_config`, that takes precedence over the
profile's proxy. Otherwise the profile's proxy is wrapped into a fresh
`ProxyConfig` automatically.

For corporate networks, `MultiloginClient` accepts an optional `proxy`
kwarg so the call to the Multilogin agent itself can route through a
gateway:

```python
from pyquotex import MultiloginClient

ml = MultiloginClient(multilogin, proxy="http://corp-proxy:8080")
profile = await ml.start_profile()
```

## Advanced Sentiment Monitoring

`SentimentMonitor` wraps the existing `sentiment` WebSocket stream
with rolling history, statistical anomaly detection, threshold
callbacks, and price/sentiment divergence analysis.

Enable it on the client:

```python
from pyquotex import Quotex, SentimentThresholds

thresholds = SentimentThresholds(
    extreme_bullish=0.7,    # bias >= +0.7 fires extreme_bullish
    extreme_bearish=-0.7,   # bias <= -0.7 fires extreme_bearish
    spike_zscore=2.5,       # |z(bias)| >= 2.5 fires spike
    divergence_window=20,
    divergence_threshold=-0.5,
)

client = Quotex(
    email="…", password="…",
    enable_sentiment_monitor=True,
    sentiment_thresholds=thresholds,
)

monitor = client.get_sentiment_monitor()

async def on_signal(signal):
    print(f"{signal.asset} -> {signal.kind} bias={signal.snapshot.bias:.2f}")

monitor.on_signal(on_signal)
```

### Signal kinds

| Kind | Trigger |
| --- | --- |
| `extreme_bullish` | Signed bias ≥ `extreme_bullish` threshold. |
| `extreme_bearish` | Signed bias ≤ `extreme_bearish` threshold. |
| `spike` | Absolute z-score of latest bias against rolling history ≥ `spike_zscore`. |
| `divergence` | Pearson correlation of bias vs price over `divergence_window` ≤ `divergence_threshold`. |

A 5-second per-`(asset, kind)` cooldown debounces repeated signals so
listeners aren't spammed during sustained extremes.

### Reading state directly

```python
latest = monitor.latest("EURUSD")             # SentimentSnapshot or None
history = monitor.history("EURUSD")           # list[SentimentSnapshot]
```

## Sentiment Persistence + Cross-Asset Correlation

`SentimentStore` is a SQLite-backed writer that persists every sample
as `(asset, timestamp, bullish, bearish, price)` rows.
`SentimentCorrelationAnalyzer` then derives cross-asset correlations
and divergence pairs from either the live monitor or the store.

```python
from pyquotex import SentimentStore, SentimentCorrelationAnalyzer

store = SentimentStore("sentiment.db")
monitor.store = store      # auto-write every feed() call

# … run for a while …

analyzer = SentimentCorrelationAnalyzer(monitor=monitor)
matrix = analyzer.correlation_matrix(
    ["EURUSD", "GBPUSD", "USDJPY"], window=30
)
divergent_pairs = analyzer.find_divergences(
    ["EURUSD", "GBPUSD", "USDJPY"], window=30, threshold=-0.4
)
```

| Method | Returns |
| --- | --- |
| `SentimentStore.write(snap, price=...)` | Persists one snapshot (idempotent on `(asset, ts)`). |
| `SentimentStore.query(asset, start=, end=, limit=)` | Snapshots in ASC order; `limit` returns the OLDEST N. |
| `SentimentStore.query_latest(asset, limit=)` | The N most-recent snapshots in ASC order. |
| `SentimentStore.assets()` | Distinct assets present in the store. |
| `SentimentCorrelationAnalyzer.correlation_matrix(assets, window=)` | `dict[(a, b), pearson_corr]`. |
| `SentimentCorrelationAnalyzer.find_divergences(assets, window=, threshold=)` | `[(a, b, corr), …]` sorted by correlation ASC. |

The analyzer can be backed by a store alone for backtests:

```python
analyzer = SentimentCorrelationAnalyzer(store=store)
```

## Auto-Reconnect with Subscription Replay

`ReconnectSupervisor` runs as a supervisor task on the API and, on
disconnect, retries with exponential backoff + jitter. After a
successful reconnect it replays the captured account mode + every
candle / all-size / mood subscription.

```python
from pyquotex import Quotex, ReconnectPolicy

policy = ReconnectPolicy(
    enabled=True,
    max_attempts=-1,        # unlimited
    initial_delay=1.0,
    max_delay=60.0,
    backoff_factor=2.0,
    jitter=0.25,
)

client = Quotex(email="…", password="…", reconnect_policy=policy)
```

Auto-reconnect is **on by default** — pass `auto_reconnect=False` (or
`ReconnectPolicy(enabled=False)`) to opt out.

### Observability

```python
sup = client.api.reconnect_supervisor
print(sup.stats.attempts, sup.stats.successful_reconnects)
print(sup.stats.last_disconnect_at, sup.stats.last_reconnect_at)
print(sup.stats.last_error)
```

### Custom rehydration hook

```python
async def warm_caches():
    await client.get_balance()

sup.on_reconnect(warm_caches)
```

The supervisor re-captures subscription state at the top of every
iteration, so subscriptions added by user code between connects are
preserved across the next drop.

## Faster Buy + Result Tracking

`v1.2.0` cut the typical hot-asset `buy()` round-trip from ~300–600ms
to ~50–150ms by removing redundant WS sends, dropping a pre-buy HTTP
call, caching subscriptions, and switching to event-driven waits.
Most of this is invisible to callers; the two visible additions are:

### `confirm_timeout` on `buy()`

```python
status, info = await client.buy(
    amount=10, asset="EURUSD", direction="call", duration=60,
    confirm_timeout=10.0,    # default 10 s — far less than duration+5
)
```

The previous behaviour blocked for `duration + 5` seconds (so 305 s
on a 5-minute trade) waiting for a confirmation that normally arrives
in under a second. The new `confirm_timeout` (default `10.0`) caps
the worst-case wait so silent failures surface fast.

### `wait_for_order_close()` — event-driven result

```python
status, profit = await client.wait_for_order_close(
    order_id, duration=60,        # sizes the default timeout
    timeout=None,                 # explicit override if you want one
)
# status: "win" | "loss"
# profit: float (negative on loss)
```

Replaces the previous 200ms polling loop in `check_win()` with an
event wait on `order_closed_<order_id>`, fired by `_on_message` the
instant the broker emits the close payload. `check_win(order_id)` is
still the canonical name; `wait_for_order_close()` is a clearer alias
for callers that aren't guessing at win/loss.

If the result is already in `listinfodata` when you call (e.g. you
got there a few hundred ms after the close), the fast path returns
instantly without hitting the event registry.

## Pending Orders (time-based and quote-triggered)

The Quotex `pending/create` flow lets you schedule a trade to fire
either at a specific future time (time-based) or when the asset price
reaches a level (quote-triggered). The wire shape was reverse-engineered
from `ws2.qxbroker.com` and verified end-to-end.

### Time-based pending — `Quotex.open_pending`

```python
status, info = await client.open_pending(
    amount=1,
    asset="EURUSD_otc",
    direction="call",       # "call"/"put" or "up"/"down"
    duration=60,            # resulting trade duration in seconds
    open_time=None,         # auto-schedule to next 60s boundary ≥ 90s ahead
    confirm_timeout=30.0,
)
print(status, client.api.pending_id)
```

Wire payload sent (matches the live web-client capture exactly):

```json
{
  "openType": 0,
  "asset": "EURUSD_otc",
  "openTime": "2026-05-05T15:01:00.000Z",
  "timeframe": 60,
  "command": "call",
  "amount": 1.0
}
```

Important field rules — these were the bugs that killed pending
orders before v1.2:

- **`openTime` must be an ISO 8601 UTC string** (`YYYY-MM-DDTHH:MM:SS.000Z`).
  Integer values trigger `{"error": "open_time_min"}` regardless of
  how far ahead they point. `Quotex.open_pending` always emits an ISO
  string for you, even when `open_time=None` (auto-schedule path).
- **`command` must be a string** (`"call"` or `"put"`). Integer
  values are accepted at create time but stored as `null` in the
  broker's order DB; when the pending fires the executor reads
  `command=null` and emits `f_pending/opened` with `error: 9` —
  the trade never actually places.
- **`duration > 0`** — passing `0` or a negative value raises
  `ValueError` immediately rather than corrupting the auto-schedule
  math.

You can pass an explicit local time via `open_time="DD/MM HH:MM"` (or
`"YYYY/DD/MM HH:MM:SS"`); the wrapper normalises it through your
profile's UTC offset before reaching the wire.

### Quote-triggered pending — `Quotex.open_pending_at_price`

> **Experimental.** Only time-based pending has been verified end-to-end
> against `ws2.qxbroker.com`. The quote-mode wire shape mirrors the
> time-mode pattern with field substitutions captured from the
> web-client modal, but has not been observed firing live. Test on a
> demo account before relying on it.

```python
status, info = await client.open_pending_at_price(
    amount=1,
    asset="EURUSD_otc",
    direction="call",
    quote=1.0852,                # trigger price level
    period="M1",                 # M1, M5, M15, H1, …
    timeout=30.0,
)
```

### Result tracking for pending orders — `check_win(pending_id)`

When a pending fires, `ws2.qxbroker` emits a sequence:

| Event | Meaning |
| --- | --- |
| `f_pending/opened` w/ `error=None` | **Pre-fire** — trade is in flight, not a rejection |
| `f_pending/opened` w/ non-None `error` | **Hard rejection** |
| `s_pending/opened` | **Success** — carries the executed-trade UUID |
| `s_orders/close` | **Settlement** — win/loss + profit |

`pyquotex` v1.2 ships a lifecycle bridge inside `_on_message` that:

1. captures `_active_pending[ticket] = asset` on `s_pending/create`,
2. tracks `pending_ticket_map[ticket] = executed_uuid` on
   `s_pending/opened`,
3. mirrors the broker's `s_orders/close` settlement back onto the
   pending ticket so `check_win(pending_id)` returns the actual
   win/loss + profit instead of timing out.

```python
status, info = await client.open_pending(
    amount=1, asset="EURUSD_otc", direction="call", duration=60,
)
# … wait for openTime …
result, profit = await client.check_win(client.api.pending_id, duration=60)
print(result, profit)        # e.g. ("win", 0.93)
```

The bridge state is cleared on every disconnect/reconnect, so stale
in-flight tickets from a dropped socket cannot cross-wire the next
pending placed on the same asset.

## Historical Data Depth — beyond the 199-candle cap

Quotex's `history/load` endpoint **caps every response at ~200 candles**
regardless of the `offset` you ask for. A naive call like
`get_candles(asset, end, offset=86400, period=60)` (asking for 1,440
candles) silently returns only the most recent ~199.

`pyquotex` ships a stitching helper that solves this by paginating
the broker request and parallelising across workers. There's no upper
bound on the total number of candles you can pull — only on
per-request size and on how aggressively the broker rate-limits you.

### Use `get_historical_candles()`, not `get_candles()`

```python
candles = await client.get_historical_candles(
    asset="EURUSD",
    amount_of_seconds=86400,    # how far back from now you want
    period=60,                  # candle size in seconds
    max_workers=5,              # parallel workers (keep ≤ 10)
)
print(f"Got {len(candles)} candles")
# Each candle: {"time": int, "open": float, "close": float,
#               "high": float, "low": float}
```

### How it works

`pyquotex/stable_api.py:409-508`:

1. Splits your `amount_of_seconds` window into `max_workers` blocks.
2. Each worker fetches its block sequentially in chunks of
   `period * 200` seconds (= 200 candles per request — the broker cap).
3. After each chunk it finds the oldest timestamp returned and asks
   for the next chunk ending there. Repeats until the block is filled
   or the broker returns an empty page.
4. All workers run in parallel under an `asyncio.Semaphore(max_workers)`.
5. Results are merged + deduplicated by timestamp and returned sorted
   ascending.

A unique monotonic `request_index` is generated per request via
`itertools.count` so parallel workers can't collide on the
event-registry key (a real bug fixed in v1.0.4).

### Sizing `amount_of_seconds`

The math is simply `amount_of_seconds = N * period`:

| Goal | period | amount_of_seconds | Roughly |
| --- | --- | --- | --- |
| 500 × 1-minute candles | 60 | 30,000 | 8.3 hours |
| 1,000 × 5-minute candles | 300 | 300,000 | 3.5 days |
| 5,000 × 1-hour candles | 3,600 | 18,000,000 | ~7 months |
| 30 days × 1-minute candles | 60 | 2,592,000 | 30 days (~43,200 candles) |

Stick to broker-supported periods: **`60, 300, 900, 1800, 3600,
7200, 14400, 86400`** (1m, 5m, 15m, 30m, 1h, 2h, 4h, 1d). Other
values may be silently rejected.

### Progress reporting

```python
def on_progress(done: int, total: int, count: int, label: str) -> None:
    pct = 100 * done // max(total, 1)
    print(f"  {label}: {pct}% — {count} candles")

candles = await client.get_historical_candles(
    "EURUSD", amount_of_seconds=30 * 86400, period=60,
    max_workers=5,
    progress_callback=on_progress,
)
```

The callback fires once per chunk per worker, so you get a real-time
view of which workers are ahead/behind.

### Ban-avoidance — read this before pulling years of data

The 200-candle-per-request cap and the `max_workers` knob exist
because Quotex aggressively rate-limits historical pulls.
Field-tested guidelines:

| Setting | When |
| --- | --- |
| `max_workers=5` (default) | Routine pulls — anything up to 30 days |
| `max_workers=2-3` | Multi-month pulls; don't trip rate limits |
| `max_workers ≤ 10` | Hard ceiling — above this gets accounts flagged |
| Cache aggressively | Historical candles never change. Save to SQLite/Parquet and only re-fetch the recent tail next time |
| Stagger huge pulls | Don't request 1 year of 1-second candles in one shot. Split by week/month, sleep between |

The library already throttles each worker with a 100ms `sleep`
between chunks (`stable_api.py:488`); don't disable that.

### Caching to SQLite — minimal recipe

```python
import sqlite3
from pathlib import Path

CACHE = Path("candles.db")
conn = sqlite3.connect(CACHE)
conn.execute("""
    CREATE TABLE IF NOT EXISTS candles (
        asset TEXT, period INTEGER, time INTEGER,
        open REAL, close REAL, high REAL, low REAL,
        PRIMARY KEY (asset, period, time)
    )
""")

# Look up the most recent cached timestamp; only fetch the gap.
cur = conn.execute(
    "SELECT MAX(time) FROM candles WHERE asset=? AND period=?",
    ("EURUSD", 60),
).fetchone()
last_ts = cur[0] or 0
gap = max(int(time.time()) - last_ts, period)

candles = await client.get_historical_candles(
    "EURUSD", amount_of_seconds=gap, period=60,
)
conn.executemany(
    "INSERT OR REPLACE INTO candles VALUES (?,?,?,?,?,?,?)",
    [("EURUSD", 60, c["time"], c["open"], c["close"],
      c["high"], c["low"]) for c in candles],
)
conn.commit()
```

Subsequent runs only re-fetch the time since the last cached candle,
turning a 30-day pull into a 5-second top-up.
