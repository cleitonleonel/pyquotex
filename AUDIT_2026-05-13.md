# Autotrader Audit — 2026‑05‑13

**Scope.** Backend at `autotrader/backend/src/autotrader/` (~13 kLOC across 33 modules), the frontend at `autotrader/frontend/`, and the small surface where autotrader touches the vendored `pyquotex/` client and root `app.py`.

**Method.** Two parallel read‑only audits (a *wiring* audit for dangling integrations, a *bug* sweep for races/leaks/logic errors), then **manual verification** of every High/Critical finding against the actual source. A handful of agent findings were rejected as confabulated and are listed at the bottom so future reviewers don't chase them again.

**Headline.** No money‑losing showstopper. The recently shipped OTP / broker‑supervisor work is sound. The biggest real gap is **no message‑level deduplication in the pipeline** — Pyrogram CAN re‑deliver an update across a reconnect, and the current code has no `(chat_id, message_id)` seen‑set, so a single signal could become two trades. There are also a handful of medium‑severity issues (a lock held across slow broker login, a sliding‑window aggregator that never closes under chatty channels, a Telegram login with no timeout) that should be fixed before scaling out.

## 1. Findings (verified, by severity)

Each finding lists: **file:line**, the symptom, the verified root cause, and a fix sketch. Items marked **✅ verified** were checked against source line‑by‑line; **⚠️ plausible** means the symptom matches the code but I didn't construct a failing test.

### 🔴 Critical → none.

Nothing in the verified set will silently lose money or corrupt persisted state under normal operation. The two areas where this *was* a risk — broker supervisor halt state and OTP exhaustion — were closed by the last week of commits (`027663e`, `ef7aead`, `8a79d72`, `b338c56`, `bc4cca5`).

### 🟠 High

#### H1. Pipeline has no message‑level idempotency ✅ verified
- **Where:** `services/pipeline.py:227` (`dispatch`) and `services/executor.py:223` (`submit`).
- **Symptom:** The same Telegram message can produce two `TradeAttempt` rows (and two real trades) if Pyrogram re‑emits it on reconnect.
- **Root cause:** `dispatch` only serialises per‑`chat_id` (line 234 `self._chat_locks[chat_id]`). Nothing checks `(chat_id, message.message_id)` against recent rows. `insert_attempt` (`models/trade_attempt.py:80`) doesn't carry a uniqueness key either. Pyrogram's `get_difference` on reconnect can replay missed updates; an editing user can also re‑emit `MessageHandler`.
- **Fix sketch:** Add a `tg_message_id: int | None` column to `TradeAttempt` (in‑place ALTER in `db.py` like the existing pattern), populate it in `executor._build_attempt`, and in `pipeline._dispatch_locked` short‑circuit with a "duplicate, ignored" decision when an attempt with the same `(chat_id, message_id)` exists in the last N minutes. The decision event keeps observability honest.

#### H2. `_do_connect` holds `QuotexManager._lock` across `client.connect()` ✅ verified
- **Where:** `services/quotex_manager.py:312–366`.
- **Symptom:** During a fresh broker login (typically 2–8 s, longer with Cloudflare retries) every other lock‑acquiring method blocks — including `disconnect()` at L478, `set_account_mode()` at L990, and the supervisor reset path at L1044.
- **Root cause:** Line 313 wraps the entire connect coroutine in `async with self._lock:`. The lock is correct in intent (serialise broker mutation) but the scope is too wide; in particular the operator clicking **Cancel** during a slow login can deadlock waiting on `cancel_connect` which itself tries to read state under the lock.
- **Fix sketch:** Split into two critical sections: (1) acquire lock → check `state in {"connecting","awaiting_otp"}` and flip to `connecting` → release. (2) await `client.connect()` lock‑free. (3) reacquire lock to write the terminal state. The `cancel_connect` path remains lock‑guarded and only needs to set `_state` and cancel `_connect_task`.

#### H3. Aggregator's sliding window never closes under chatty channels ✅ verified
- **Where:** `services/parsers/aggregator.py:90`.
- **Symptom:** A channel that posts unrelated chatter every < `window_seconds` keeps the per‑sender buffer alive indefinitely. A late, unrelated message can then re‑trigger the inner parser against ageing context and emit a corrupted signal.
- **Root cause:** `buf.expires_at = now + self._window` is unconditional on every `feed()`. There is no *absolute* age cap — only a max‑messages cap (line 91).
- **Fix sketch:** Track `buf.first_seen_at` and refuse to extend the window past `first_seen_at + max_total_age`. A sensible default is `window_seconds * 3`. Drop and emit a `ParseError` reason on eviction so the decision feed records it.

### 🟡 Medium

#### M1. Telegram login has no timeout on `client.connect()` / `client.send_code()` ✅ verified
- **Where:** `services/telegram_manager.py:306–307`.
- **Symptom:** A hung Telegram MTProto socket wedges `begin_login` forever; the API endpoint either times out at the reverse proxy or holds the manager lock indefinitely.
- **Fix sketch:** Wrap both awaits in `asyncio.wait_for(..., timeout=20)` and convert `TimeoutError` to a `TelegramManagerError` so the UI shows "login timed out — retry?". Same treatment for `submit_code` and `submit_password` (lines ~340/~370 in same file).

#### M2. `prep_trigger` drops expired preps silently ⚠️ plausible
- **Where:** `services/parsers/prep_trigger.py` (eviction path; agent cited ~L303–304, but the module is 321 lines and the exact eviction line wasn't re‑verified — confirm before fixing).
- **Symptom:** A two‑phase channel that posts "EUR/USD prep" then has a network gap before the "BUY 1m" trigger gets the prep silently discarded; the trigger arrives, fails to match, and the operator sees nothing.
- **Fix sketch:** Emit a `pipeline.decision` event with `outcome="prep_expired"` when the prep is evicted *and* the chat is `enabled` in `watched_channels`. Costs one row per eviction in the decisions feed; massively improves debuggability.

#### M3. `_status_watcher_task` spawn is not atomic ✅ verified (low likelihood)
- **Where:** `services/quotex_manager.py:502–516`.
- **Symptom:** Two concurrent callers can both pass the `is None` check and both `create_task`, leaking the second watcher.
- **Real‑world likelihood:** Low — the only call sites are the connect path (single‑flighted by `_connect_task`) and `set_account_mode`. But it's a latent footgun for future refactors.
- **Fix sketch:** Move the spawn under `self._lock` (after H2 is split this is trivial), or use a `compare_and_swap` pattern with `asyncio.current_task()`.

#### M4. WebSocket auth errors swallowed without telemetry ✅ verified
- **Where:** `routers/feed.py:38–42`.
- **Symptom:** Operators report "WS won't connect" with no log breadcrumb. The `except Exception:` at L40 catches `InvalidToken` (raised by `_decode`), `HTTPException` (also raised by `_decode`), and anything else, then closes with 1008 silently.
- **Fix sketch:** Catch `HTTPException`/`InvalidToken` explicitly, `log.warning("feed.ws.auth_rejected", reason=type(exc).__name__)`, and let unexpected exceptions propagate so they show up in `log.exception` at the framework boundary.

#### M5. Float arithmetic on money paths ⚠️ plausible, low business risk today
- **Where:** `models/martingale_state.py:69–75` and `services/risk_gate.py:217–224`.
- **Symptom:** `last_payout = last_stake + last_profit` (line 75) stores a `float`. `_round_stake` is applied at the executor boundary so the bug doesn't reach the broker, but the *ladder base* carried forward accumulates rounding noise across long winning streaks.
- **Fix sketch:** Round to 2 decimals at the persistence boundary (`record_outcome` should `round(last_payout, 2)`). Long‑term, migrate money columns to `Decimal`/`Numeric(12, 2)` — but that's a multi‑file refactor and outside this phase.

#### M6. `_do_connect`'s catch‑all swallows auth failures alongside cancellation ⚠️ plausible
- **Where:** `services/quotex_manager.py:367–401` (the recovery comment block is correct in intent; verify the runtime behaviour).
- **Symptom:** A genuine credential‑rejection from the broker is logged at `WARNING` (`broker.connect.rejected`) but doesn't differentiate from a transient Cloudflare 403, so the dashboard's "error" state is ambiguous.
- **Fix sketch:** Map known auth strings ("invalid credentials", "captcha required") to distinct `_last_error` codes the dashboard can present specifically.

## 2. Things the audit found CLEAN

Don't redo this work in a future pass — these were checked and are fine:

- **Event bus topic symmetry.** Every consumed topic has a publisher and vice versa, except `broker.otp_required` (L1 above).
- **All `asyncio.create_task` sites store the reference and add a `discard` callback** — no orphan‑GC class of bug. Specifically: `executor._watchers` (set + done_callback), `quotex_manager._connect_task`, `quotex_manager._status_watcher_task`, `telegram_manager._prime_task`, `admin_bot_notify._digest_task`, `backup_scheduler._task`.
- **Locks all use `async with`** — no manual acquire/release; no held‑across‑exception leaks. The H2 finding is about *scope*, not safety.
- **DB migrations are transactional.** `db.init_db()` wraps every ALTER in `engine.begin()` (line 49). The audit‑agent's "non‑transactional ALTER" claim is a false positive.
- **`update_attempt` handles `profit=0.0` correctly.** `0.0 is not None` is `True` in Python — a losing trade with zero profit DOES persist. Another agent false positive.
- **Auth uses Argon2 + Fernet** — both have constant‑time primitives internally; no `==`‑on‑secrets pattern anywhere in `auth.py`/`crypto.py`.
- **OTP relay state machine** is correct as of `b338c56`: plain‑text submissions during the active cycle work, exhaustion closes the prompt, `/reconnect` resets the gate, the supervisor halts via `_stopping`.
- **Frontend↔backend route surface** matches: every route the Next.js app calls exists, and every backend route that isn't internal (stats/admin/health) is consumed.
- **Background task lifecycle on shutdown** is correct (`main.py:361`, `executor.shutdown()`, `admin_bot_notify.shutdown()`).
- **Reconciler on startup** (`executor.reconcile_pending`) handles all three buckets (`placed_at is None`, in‑window, past‑settled) without ticking the martingale ladder — the right call when outcomes aren't recoverable.

## 3. Phased remediation plan

Each phase is **independently shippable** — ends in a green test run and a commit that can land on `master` without depending on later phases. Each phase is small enough to ship in a single sitting (target: ≤ 200 LOC diff, ≤ 1 hour of focused work).

### Phase 0 — Instrumentation only (no behaviour change) — *1 PR*
**Goal:** Measure the real‑world rate of each suspected bug before fixing it. This is a trading bot — speculative fixes are worse than well‑understood bugs.

1. Add a structured log line `pipeline.duplicate_candidate` in `pipeline._dispatch_locked` that fires *whenever* a message arrives for a chat that already has a `TradeAttempt` with the same minute‑bucket + asset (cheap heuristic, no schema change). This will tell us H1's prevalence in production.
2. Add `broker.lock.contention` log when `quotex_manager._lock` is *awaiting* > 500 ms. One extra line per slow login. Quantifies H2's blast radius.
3. Add `aggregator.window_extended` debug log with `(chat_id, age_seconds, message_count)` every time `expires_at` is pushed past `first_seen_at + window_seconds`. Quantifies H3.
4. Add `feed.ws.auth_rejected` (M4) and `telegram.login.timeout_candidate` (M1, log the elapsed time on any `send_code` that took > 5 s, even if it succeeded). Cheap probes.
5. **Tests:** unit tests assert the new log lines are emitted under their conditions; production behaviour unchanged.

**Ship criterion:** All existing tests still pass; new tests cover each instrumentation point; deploy to staging for 24 h and capture the metrics.

### Phase 1 — Bounded scope, high‑value fixes — *1 PR*
**Goal:** Close the verified medium‑severity ergonomic issues that don't touch money math. Lowest blast radius of the "fix" phases.

1. **M1 — Telegram login timeouts.** Wrap `client.connect`, `send_code`, `sign_in`, `check_password` in `asyncio.wait_for(20s)`. ~15 LOC.
2. **M4 — WebSocket auth error logging.** Replace bare `except Exception` with `except (HTTPException, InvalidToken)` and a `log.warning`. ~5 LOC.
3. **L4 — drop dead `consumer_task` cleanup in `routers/feed.py`.** ~6 LOC removed.
4. **L1 — drop `broker.otp_required` publish** (or add a one‑line comment "reserved for future subscribers"; team's call). ~5 LOC.
5. **L7 — html.escape the OTP prompt** on the status payload boundary. ~3 LOC.
6. **Tests:** extend `test_telegram.py` for the new timeout, extend `test_health.py` (or add `test_feed_auth.py`) for the WS rejection log.

**Ship criterion:** Phase 0 metrics confirm Phase 0 is wired correctly; full suite green.

### Phase 2 — Pipeline idempotency (H1) — *1 PR*
**Goal:** Close the only verified path that can produce duplicate real trades. The biggest single risk reduction in the audit.

1. Schema: add `tg_message_id: int | None` to `TradeAttempt`, follow the existing `db._migrate_in_place` pattern. Indexed via composite `(chat_id, tg_message_id)`.
2. Plumb `message.message_id` through `pipeline._dispatch_locked` → `executor._build_attempt`.
3. In `_dispatch_locked`, before building parsers, query for a recent attempt with the same `(chat_id, tg_message_id)` within the last 10 minutes; if present, emit a `pipeline.decision` with `outcome="duplicate"` and return.
4. Phase 0 metric `pipeline.duplicate_candidate` becomes a real `duplicate` decision.
5. **Tests:** new `test_pipeline_idempotency.py` covering the replay‑within‑window and replay‑outside‑window cases; assert no duplicate `TradeAttempt` row inserted.

**Ship criterion:** Phase 0 metric confirms the new path catches duplicates that were previously slipping through (or confirms there are zero duplicates in production, in which case the protection is preventative).

### Phase 3 — Broker lock scope (H2) and aggregator window cap (H3) — *2 PRs (one each)*
**Goal:** Close the two remaining High findings. Each is isolated to one file; ship them as separate PRs to keep blame ranges clean.

1. **H2** in one PR: split `_do_connect`'s lock into the three sections described in §1. Existing `test_broker_resilience.py` already exercises connect/disconnect concurrency; extend to cover "click cancel during slow connect" (asyncio test with a slow Quotex stub).
2. **H3** in one PR: add `first_seen_at` to `_Buffer`, cap `expires_at` at `first_seen_at + max_total_age` (default `window_seconds * 3`, configurable). New test in `test_parsers.py` for the "chatty channel" eviction case.
3. **M3** rides along with H2 (the spawn becomes atomic for free once `_lock` covers it). ~1 LOC if any.

**Ship criterion:** Per‑PR: full suite green, integration test exercising the specific race passes.

### Phase 4 — Cleanup & ergonomics — *1 PR, optional*
Pure housekeeping, no behaviour change:

1. **L2** remove `account_type_int`.
2. **L3** decide: wire `/auth/me` into the UI header (username chip), or remove the route.
3. **L5** move `_TICKER_ALIASES` to `ParserConfig` so operators can teach the bot new tickers without a code deploy.
4. **L6** `AUTOTRADER_MUTE_LOGGERS` env var.
5. **M5** `round(last_payout, 2)` in `martingale_state.record_outcome` — keep `float` for now, file an issue for the eventual `Decimal` migration.
6. **M6** Map known broker auth strings to distinct `_last_error` codes; surface in the dashboard.

**Ship criterion:** All findings in §1 Low table are either closed or have an issue filed with the chosen disposition.

### Phase 5 — Long‑horizon (out of scope for this audit) — *file issues, do not ship now*

1. Migrate money columns to `Numeric(12, 2)` (large refactor; needs a real Alembic setup first).
2. Replace the in‑place `_migrate_in_place` migration system with Alembic. The in‑place approach is fine *today* but each new column adds friction.
3. Persist event‑bus events to disk for replay/debugging — would have made auditing the OTP flows trivial.
4. Frontend retry/backoff on transient `5xx` from `lib/api.ts` — currently surfaces immediately.
